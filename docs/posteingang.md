# Posteingang: работа сотрудника и эксплуатация

Posteingang принимает приватный PDF, предлагает факты и действия, а сотрудник проверяет оригинал и подтверждает итог. Только подтверждение создаёт задачи. Предложенная AI дата и подтверждённый внешний срок отделены от внутреннего срока работы Task.

Рабочий экран: **Kanzlei → Posteingang / Входящие PDF**, маршрут `/desk/posteingang`. Подтверждённое письмо также доступно в **Customer → Dokumente** и через источник созданной Task. Результаты проверки готовности находятся в [отчёте AP-10](acceptance/ai-posteingang.md); правила данных — в [contracts](plans/ai-posteingang/contracts.md).

## Доступ и ответственность

- **Posteingang Operator** явно назначается активному System User, который принимает и проверяет письма. Для одного Steuerberater эту роль назначают ему; отдельный сотрудник для роли не требуется. Установка приложения роли пользователям не назначает.
- Оператору нужны текущие права Customer. Для выбора Mandant и подтверждения — Customer read/write; при создании задач также Task create. Исполнитель должен быть активным System User с доступом к этому Customer.
- **System Manager** настраивает провайдера и секрет. Для административного исправления дополнительно нужны Operator и права затронутого Customer. System Manager без Operator не получает рабочую очередь.
- Подтверждённую историю через Dokumente/Task читает сотрудник с необходимыми текущими правами Customer/Task; Operator для такого чтения не нужен. Назначение задачи, владение и DocShare не заменяют эти проверки. Guest, Website User и отключённые пользователи не получают доступ.

До начала работы владелец назначает ответственного за ежедневный разбор очереди и ошибок, а также порядок эскалации на время отсутствия. При одном сотруднике ответственным может быть сам Steuerberater. Это организационная запись, система не назначает ответственного автоматически.

## Основной процесс

Рабочая страница использует штатные поля, кнопки и диалоги Frappe. Очередь
отделена от проверки письма; на широком экране оригинал PDF и текущий этап
видны рядом. На узком экране кнопки **Original-PDF / Оригинал PDF** и
**Zurück zur Prüfung / Вернуться к проверке** переключают представление,
сохраняя текущий этап и черновик.

1. В очереди выберите **Zu prüfen / К проверке**, **In Verarbeitung / В обработке**,
   **Klärung erforderlich / Требует уточнения** или **Erledigt / Завершённые**.
   К проверке относятся Received, Needs Review и Error; в обработке — Queued и
   Processing. Расширенные фильтры сохраняют выбор точного состояния и автора.
2. Нажмите **PDF hochladen / Загрузить PDF**, выберите один или несколько PDF.
   Укажите дату получения либо оставьте «неизвестна». Текущая дата не подставляется;
   общая дата применяется к пачке только явно. Каждый файл получает свой результат:
   новая запись, доступный дубль или ошибка. Ошибка одного не отменяет остальные.
   Дубль открывает существующее письмо без второго оригинала и нового анализа.
3. Откройте письмо. При необходимости запустите анализ либо переключитесь на
   ручную проверку. Результат анализа сохраняется как предложение; **Neuestes
   Analyseergebnis übernehmen / Применить последний результат анализа** явно
   переносит его в черновик. Замена изменённого черновика требует подтверждения.
4. **Dokument und Mandant / Документ и клиент.** Проверьте оригинал, отправителя,
   дату документа, тип и краткое содержание. Дата получения и время загрузки
   показаны отдельно. Явно выберите Mandant с причиной, даже при единственном
   кандидате; при необходимости используйте поиск. Несколько адресатов требуют
   уточнения. **Speichern und fortfahren / Сохранить и продолжить** открывает
   следующий этап только после успешного сохранения.
5. **Aufgaben und Fristen / Задачи и сроки.** Для каждого действия явно выберите
   принятие или отклонение. При отклонении появляется обязательная причина.
   Для принятой задачи выберите исполнителя и внутреннюю дату работы. Варианты
   «назначить позже» и «запланировать позже» раскрывают причины и означают,
   что задаче требуется планирование. **Frist aus dem Schreiben / Срок из письма**
   отделён от внутренней даты; подтверждённая внешняя дата требует основания,
   относительный срок автоматически не вычисляется. Если все действия отклонены
   или их нет, заполните причину отсутствия задач. Пустой OCR и ошибка анализа
   не являются решением «без действий». Затем сохраните и откройте итог.
6. **Abschluss / Подтверждение.** Проверьте Mandant, факты письма, принятые и
   отклонённые действия, назначения, даты и основания. Кнопки изменения возвращают
   на соответствующий этап. Новый неприменённый Run требует применения либо
   причины сохранения прежнего черновика. Отдельно отметьте проверку оригинала
   и всех окончательных решений, затем подтвердите создание указанного числа
   задач либо завершение без задач. До этого момента задачи не создаются.
7. После подтверждённого ответа остаётся экран результата со ссылками на доступные
   Task. Следующее письмо открывается только по **Nächstes Dokument prüfen /
   Проверить следующий документ**; можно вернуться к очереди. Отсутствие доступа
   к созданной Task не означает отсутствие созданных задач.

Для неполного документа используйте уточнение с обязательной причиной.
Результат загрузки или записи с неизвестным исходом проверяется и повторяется
тем же намерением; не создавайте новую загрузку или подтверждение с изменёнными
данными. При потере ответа загрузки откройте диалог снова: незавершённый ключ
можно проверить, а для неизвестного результата потребуется выбрать тот же файл.

Правки сбрасывают отметку человеческой проверки. При новом Run можно применить его или явно сохранить прежний черновик с причиной. Изменение Customer, источника или управления анализом при несохранённом черновике требует сначала сохранить либо отбросить правки.

Сохранение явное, автосохранения и автоматического merge нет. При конфликте ревизий сравните локальную и серверную версии. Старые правки не получают новую ревизию автоматически. При неизвестном исходе mutation повторяйте тот же запрос через предложенное действие; не создавайте новое намерение с изменённым payload. Потеря доступа очищает PDF и защищённые подписи.

## Задачи и исправления

В Task внутренний срок отображается в календаре. Секция источника показывает защищённый PDF, подтверждённый внешний срок, основание и evidence. Отсутствие подтверждённого внешнего срока обозначается явно. Документ не копируется в описание задачи и не переносится в Suite Drive.

После подтверждения рабочие поля Task изменяются обычными разрешёнными операциями ERP. Происхождение и Customer нельзя снять, заменить или обойти через Duplicate. Завершённые/отменённые задачи не считаются ожидающими планирования.

При ошибочном подтверждении администратор с нужными правами выбирает **Korrektur anlegen / Создать исправление** и вводит причину. Замена получает собственный приватный File; можно явно использовать исходные байты или загрузить новый PDF. Customer, Run, решения и назначения автоматически не переносятся, анализ автоматически не запускается.

Исходное письмо и его задачи остаются в карантине. Администратор использует **Ursprüngliche Aufgabe prüfen / Разобрать исходную задачу** для каждой старой Task: отменённая обычным механизмом ERP либо сохранённая как история с причиной. Completed Task сохраняет Completed. После разбора замену может подтвердить обычный разрешённый оператор. Старые задачи не перепривязываются к новому Customer; карантин исходника в MVP не снимается.

## Настройки и остановка обработки

**Posteingang-Einstellungen / Настройки входящих писем** доступны System Manager.

| Настройка | Поведение |
|---|---|
| `enabled` | Разрешает новый приём и обычные операции проверки; default `0`. Чтение подтверждённой истории, отмена и административное исправление сохраняются при выключении |
| `provider=fake` | Автономная проверка только известных синтетических fixture hashes; неизвестный PDF не получает выдуманный результат |
| `external_analysis_enabled` | Разрешает внешние запросы Mistral; default `0`. Для fake не требуется |
| `auto_analysis_enabled` | Анализ только новых загрузок после commit; default `0`. Включение не запускает накопленные письма |
| `ocr_model`, `extraction_model` | Конкретные версии; `latest`, URL и некорректные имена запрещены. В исходной конфигурации указаны `mistral-ocr-4-1` и `mistral-small-2603`; доступность перед live-проверкой подтверждается отдельно |
| `max_file_bytes`, `max_pages`, `max_actions` | Потолки 20 MiB / 50 страниц / 30 действий; настройки могут уменьшить лимиты. Документ и действия не обрезаются молча |
| `max_retries` | Технические повторы только типизированных временных ошибок. Неизвестный исход запроса не является разрешением повторить его автоматически |

Секрет вводится только в Password-поле Settings. Не передавайте его в чат, CLI-аргументах, исходниках, журнале или git. Сохранение Settings не проверяет ключ сетевым запросом. При ротации введите новый секрет и сохраните: сервер повышает configuration epoch. Смена ключа, моделей, переключателей или лимитов делает старые Runs неприменимыми; даже возврат прежних значений не восстанавливает старый epoch. Маска пароля не считается новым ключом.

Чтобы остановить внешние запросы, выключите внешнюю обработку; для остановки нового приёма и обычных записей выключите функцию целиком. Уже отправленный HTTP-запрос отозвать нельзя, но поздний результат проходит guards перед сохранением. После обнаруженного отключения/отзыва прав Run останавливается. Повторное включение само его не возобновляет: оператор явно запускает новое поколение.

## Ежедневный разбор и зависшие задания

Ответственный проверяет возраст незавершённых писем, **Error / Ошибка**, **Needs Clarification / Требует уточнения**, безопасный код ошибки и время ожидаемого повтора. Операционная очередь уже находится на рабочем экране; отдельного автоматического внешнего мониторинга этот этап не добавляет.

| Ситуация | Действие |
|---|---|
| `Queued`, worker не начинает | Проверить worker очереди `long`, Redis и доставку durable Run. Не создавать второй анализ из Queued/Processing |
| Временный отказ провайдера | Сверить число попыток и `next_attempt_at`; backoff хранится в БД. Worker не ждёт через sleep |
| `WORKER_INTERRUPTED` / неизвестный исход | Сначала выяснить состояние текущего Run. Recovery завершает просроченный lease; автоматической повторной отправки нет. При необходимости — явный новый запуск, который может использовать валидный OCR checkpoint |
| `ANALYSIS_STOPPED` | Проверить пользователя, Operator, Customer/File доступ, переключатели и epoch. После исправления причины — явный новый запуск |
| `CONFIGURATION_INVALID` | System Manager проверяет конкретные модели и секрет в Settings; ошибка не содержит provider response/секрет |
| `OCR_FAILED`, `INVALID_RESULT`, `LIMIT_EXCEEDED` | Проверить оригинал и перейти к ручному разбору/уточнению. Не трактовать как отсутствие действий и не увеличивать глобальные лимиты без разбора причины |

Recovery зарегистрирован раз в минуту, но фактический интервал ограничен scheduler tick Bench и может быть около четырёх минут. `recovery_interval_seconds` — минимальный интервал между sweep, а не обещание секундного старта. Общий scheduler tick не менять ради Posteingang. Выключение AI не отменяет cleanup/recovery уже незавершённых Runs. При недоступной БД worker может оставить lease для последующего разбора.

При эскалации сообщайте письмо/Run, безопасный код, время и последнее действие. Не копируйте PDF, OCR, prompts, причины и ключи в технические логи или общедоступные каналы.

## Хранение и разрешённый контур

Оригинал, OCR, Run, черновики и audit history имеют защищённое хранение. Сроки хранения производных данных и порядок удаления утверждает владелец до использования реальных документов. Автоматического retention/purge для неизменяемых Run/Event/истории этот этап не реализует; не удаляйте их прямым SQL в рабочем контуре.

Адаптер передаёт PDF в теле OCR-запроса Base64. Он не создаёт Mistral Files uploads, публичные/presigned URL или временные PDF. Очистка удалённых uploads здесь **NOT APPLICABLE**; отдельный фиктивный cleanup job не нужен. Локальные evaluation artifacts могут содержать синтетический OCR/extraction и хранятся отдельно от логов и git.

Техническая готовность с fake не является допуском Mistral или реальных клиентских документов. Для реальных данных владелец отдельно разрешает провайдера/контур, организационные условия, расходы, сроки хранения и ответственных. Live-оценка на синтетических документах тоже запускается отдельно, а не обычными тестами.

## Автономная оценка AP-10A

Набор: 42 синтетических письма, 12 development и 30 holdout. Старые 16 кейсов сохраняют исходные PDF и индивидуальные gold-файлы. Смысловые annotations отделены от fake extraction. Плохой скан остаётся в знаменателе полноты действий даже при пустом OCR. Прежние четыре holdout использовались в contract-проверках; новые 26 показываются отдельно. Holdout не используется для настройки prompt.

Из корня репозитория подготовленным инструментальным Python:

```sh
python scripts/validate_posteingang_fixtures.py
python scripts/validate_posteingang_fixtures.py --pilot-profile ap10-v1
python scripts/evaluate-posteingang.py --help
python scripts/run_posteingang_evaluation.py --help
```

`--help` не требует Frappe и не пишет в БД. Для collection нужен Python Bench и новый одноразовый сайт с установленными ERPNext/kanzlei_erp. Сборщик не создаёт сайт. Ниже `posteingang-ap10.localhost` — имя такого заранее созданного сайта; основной сайт использовать нельзя. Перед первым сбором администратор помечает только этот одноразовый сайт:

```sh
cd /workspace/development/frappe-bench
bench --site posteingang-ap10.localhost set-config posteingang_acceptance_site true
env/bin/python /workspace/scripts/run_posteingang_evaluation.py \
  --site posteingang-ap10.localhost \
  --actor ap10-evaluation-01@example.invalid \
  --provider fake --split all --max-documents 42 \
  --output /workspace/artifacts/posteingang-evaluation/ap10-fake-42
```

Для нового измерения используйте свежего `ap10-…@example.invalid` actor и свежий одноразовый сайт. Нельзя принять успешный fake/старый Run за новый Mistral результат. Если те же PDF уже приняты другой measurement, сборщик откажет: создайте новый одноразовый сайт, а не меняйте bytes/hash ради обхода дублей. Сборщик использует свою RQ-очередь и worker без остановки общих процессов; автоматического подтверждения писем нет.

Продолжение прерванного сбора использует те же site, actor, provider, split, output и лимиты плюс `--resume`:

```sh
cd /workspace/development/frappe-bench
env/bin/python /workspace/scripts/run_posteingang_evaluation.py \
  --site posteingang-ap10.localhost \
  --actor ap10-evaluation-01@example.invalid \
  --provider fake --split all --max-documents 42 \
  --output /workspace/artifacts/posteingang-evaluation/ap10-fake-42 --resume
```

Resume проверяет journal/fingerprints. Завершённые результаты не отправляются повторно. Изменившийся код/набор/конфигурация или неизвестный исход worker требуют разбора; `--resume` не является разрешением на скрытый платный повтор. Сохраняйте `journal.json`, `observations.json` и `judgments.json` вместе. Не редактируйте наблюдения ради улучшения процента.

Сгенерированные judgments сначала `pending`. Независимый проверяющий заполняет смысловые one-to-one соответствия действий и фактов; совпадения заголовков недостаточно. Спорные случаи разрешаются вторым проверяющим. Не выдавайте автоматически сопоставленный fake за человеческую gold-проверку.

После заполнения judgments отчёт строится без сети и БД:

```sh
cd /workspace
python scripts/evaluate-posteingang.py \
  --manifest kanzlei_erp/tests/fixtures/posteingang/manifest.json \
  --observations artifacts/posteingang-evaluation/ap10-fake-42/observations.json \
  --judgments artifacts/posteingang-evaluation/ap10-fake-42/judgments.json \
  --output artifacts/posteingang-evaluation/ap10-fake-42/report
```

Используйте Python инструментального окружения с jsonschema; Bench collection запускается его собственным `env/bin/python`. Отчёт содержит JSON и Markdown с дробями, знаменателями и case IDs ошибок. Код возврата `0` означает корректное построение отчёта, а не допуск. `--require-gates` даёт ненулевой код при FAIL/NOT MEASURED; fake никогда не получает live-quality GO. Невалидные входы дают отдельный отказ. Не передавайте gold/catalog/reviews/ожидаемые Tasks в Mistral запросы.

## Условия AP-10B

AP-10B остаётся отдельным live-измерением. Владелец разрешает конфигурацию и расходы; затем проверяются актуальные официальные модели/endpoints, development smoke, freeze и 30 holdout. Сборщик live дополнительно требует `--provider mistral --allow-external --max-requests …`, настроенный Mistral в Settings, выключенный автозапуск и `max_retries=0`. Ключ по-прежнему вводится только в Settings. Эти флаги не означают, что live уже выполнен или разрешены реальные документы.

Полнота действий должна быть ≥95%, точность ≥90%, полнота действий с явным сроком и правильность явных дат — 100%; самовольно вычисленных relative dates — 0. Пороги Mandant/evidence, случаи неопределённости и все знаменатели определены в contracts. Ошибки обработки и отсутствующие результаты не исключаются из полноты.

Для ускорения нужен заранее зарегистрированный замер: минимум два участника, каждый в ручном и AI-assisted режиме на разных письмах. Одному сотруднику нельзя сначала дать письмо вручную, затем повторно засечь то же письмо с AI. Активное время и ожидание OCR учитываются отдельно; медиана отношений по сопоставимым группам должна быть ≤0.70. При одном Steuerberater можно провести описательный usability-разбор, но этот порог остаётся **NOT MEASURED**, без понижения требований.

Фактическая стоимость требует billing/usage export с периодом, валютой и основанием распределения. `attempt_count` не равен числу HTTP-запросов и не доказывает расходы. Без источника стоимость — **NOT MEASURED**, оценка по тарифу помечается отдельно. Для отчёта доступны `--timings` и `--billing`; схемы находятся в `docs/plans/ai-posteingang/evaluation/`.

Решение о пилоте: `GO_SYNTHETIC_PILOT`, `NO_GO` или `INCOMPLETE`. Обязательный FAIL/NOT MEASURED не даёт GO. AP-10A может быть готов при AP-10B NOT RUN; весь AP-10 тогда остаётся открытым. Допуск реальных документов и deployment выполняются отдельным решением владельца.
