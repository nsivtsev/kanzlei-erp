# GitHub Actions → Hetzner deployment

The production stack is a single site on an x86-64 Ubuntu 24.04+ or Debian 12+ server. GitHub builds
an image containing Frappe, ERPNext and this app, verifies it on a disposable site,
publishes it to `ghcr.io/nsivtsev/kanzlei-erp`, and deploys the verified **digest** over
SSH. Caddy provides public HTTPS. The first deployment creates an empty site; local
development databases, email archives and credentials are never copied.

## Prepare the server once

Use a clean server with enough memory for ERPNext and sufficient disk for the database,
site files, images and seven full backups. A deployment pauses application services
while backing up and migrating, so choose a maintenance window.

1. Point the domain's DNS A record to the server. Add AAAA only if IPv6 is configured.
   Allow inbound SSH and TCP 80/443 in the Hetzner firewall. Database and Redis ports
   are internal; the frontend's debug port binds to loopback only.
2. Generate a dedicated Actions SSH key on your workstation, without a passphrase:

   ```bash
   mkdir -p ~/.ssh
   ssh-keygen -t ed25519 -f ~/.ssh/kanzlei-deploy -C github-actions-kanzlei
   ```

3. Copy `scripts/bootstrap-production.sh` and **only `~/.ssh/kanzlei-deploy.pub`** to the server
   using your existing administrative access. Run as root:

   ```bash
   bash bootstrap-production.sh erp.example.com ops@example.com ./kanzlei-deploy.pub
   ```

   This installs Docker from its signed repository, creates `deploy`, authorizes the
   key, and prepares `/opt/kanzlei-erp`. Rerunning it preserves existing credentials.
   Membership in the Docker group gives `deploy` privileges equivalent to root.
   Keep this key limited to deployment use.

4. The generated `/opt/kanzlei-erp/shared/production.env` is readable only by `deploy`
   (mode 600). `DOMAIN` and `SITE_NAME` must match. The generated hexadecimal database
   and Administrator passwords stay on this server. The format is plain `KEY=value`,
   with no shell quoting or substitutions; see `deploy/production.env.example`.
   Do not change the project name or database password after creating the volumes.
5. Ensure `deploy` can pull the GHCR package. Public packages need no login. For a
   private package, use a separate GitHub token with `read:packages` and authorize it
   for the organization when required. As `deploy`, enter it interactively:

   ```bash
   docker login ghcr.io --username YOUR_GITHUB_USERNAME
   ```

   The Actions `GITHUB_TOKEN` publishes images; the server's token only reads them.
   Grant this repository Actions write access to the package if an existing package
   is not already associated with it.

## Configure GitHub

In repository **Settings → Environments**, create `production`. Configure:

| Type | Name | Value |
| --- | --- | --- |
| Secret | `DEPLOY_SSH_KEY` | Complete private `kanzlei-deploy` key, including BEGIN/END lines |
| Secret | `DEPLOY_KNOWN_HOSTS` | Verified OpenSSH known_hosts entry for the server |
| Variable | `DEPLOY_HOST` | Server IPv4 address or SSH hostname |
| Variable | `DEPLOY_SSH_PORT` | Optional; default `22` |
| Variable | `DEPLOY_SSH_USER` | Optional; default `deploy` |
| Variable | `DEPLOY_PATH` | Optional; default `/opt/kanzlei-erp` |
| Variable | `PRODUCTION_URL` | `https://erp.example.com` |

Verify the host fingerprint using the Hetzner console or another trusted channel:

```bash
# On the server via the trusted console:
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
# On your workstation; compare the fingerprint before trusting the entry:
ssh-keyscan -p 22 -t ed25519 SERVER_IPV4 > kanzlei-known-hosts
ssh-keygen -lf kanzlei-known-hosts
```

Store the verified file contents in `DEPLOY_KNOWN_HOSTS`. A nonstandard SSH port uses
the `[hostname]:port` known_hosts form generated by `ssh-keyscan`. The pipeline uses
strict verification and fails when a server key changes.

Allow deployment of `v*` tags in the environment's deployment rules if rules are
enabled. Manual dispatch runs can be associated with `main`, so permit `main` too
if using that recovery path. No additional approval step is required by these files;
repository administrators can choose environment reviewers separately.

## Release

Merge the deployment branch and reviewed application changes into `main`. PRs and
pushes to `main` run the image build, deployment safety tests, full app tests, HTTP
and assets checks, and a real database/public/private-files backup and restore.
Tests create their own Docker project and delete only its disposable volumes.

Create an immutable release tag on the reviewed `main` commit:

```bash
git switch main
git pull --ff-only
git tag -a v1.0.0 -m 'First production release'
git push origin v1.0.0
```

Tags must be `vX.Y.Z` without prerelease suffixes and must point to a commit reachable
from `main`. Never move an existing release tag. A normal deployment rejects older
versions and reassignment of the current version to another image or commit.

The release workflow tests the exact image before publishing it; it does not rebuild
after testing. If a tag already exists in GHCR, it verifies the image's commit label,
pulls and tests that exact digest again, and reuses it without overwriting the tag.
Registry authentication/network failures stop the release rather than permitting a
new publication. Its summary records the tag, commit and digest. Workflow concurrency
queues releases without canceling an active migration, and the server also enforces
an exclusive deployment/restore lock. GitHub's queue support is documented
[here](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

For a retry **before server changes**, run **Actions → Release and deploy → Run
workflow** on `main`, specifying the existing tag. An unfinished migration requires
the explicit recovery procedure below; clicking rerun does not bypass that guard.

After the first deployment, open the HTTPS URL and log in as `Administrator` with
the generated password from `shared/production.env`. Complete ERPNext's setup wizard
and configure the company, staff permissions and mailbox accounts. The initial site
uses German and `Europe/Berlin`; subsequent migrations preserve user language
preferences. No production application tests or sample-data scripts run on the server.

## What an update does

The server pulls the digest and verifies its commit label, then enables maintenance,
stops the web, workers and scheduler, and makes a complete pre-update backup. Each
snapshot under `/opt/kanzlei-erp/backups/` contains:

- `database.sql.gz`, `public.tgz`, `private.tgz` and `site_config.json`, including the
  site's encryption key needed to decrypt stored credentials;
- the server's `production.env`, the previous release's deployment configuration,
  image digest, commit and tag;
- a manifest with SHA-256 checksums for every saved file.

Backup directories use mode 700 and saved files mode 600. The update does not migrate
until backup and checksum verification succeed. A backup failure resumes the old
application when its maintenance process has been stopped safely. After migrations,
the pipeline checks login, API, built JS assets and service stability before recording
the new current release. Last seven verified complete snapshots are retained after
a successful deploy; incomplete snapshots do not count toward that limit.

Backups are **local pre-update snapshots only**. They do not protect against losing
the server/disk or cover changes between deployments. Off-server copies and scheduled
backups require a separate operational setup. Keep sufficient free disk space; the
pipeline never prunes production volumes or images automatically. This backup format
expects Frappe's `Encrypt Backup` setting to remain disabled; the snapshots rely on
server access controls and include sensitive site credentials.

## Diagnose and recover

Connect as `deploy`. `shared/current.json` and `current` identify the last committed
release; `shared/pending.json` records an unfinished operation and its backup. A
migration or post-migration failure leaves application services stopped and the site
in maintenance. It never automatically switches older code onto a changed schema.

```bash
cd /opt/kanzlei-erp
cat shared/current.json
cat shared/pending.json
docker ps -a --filter label=com.docker.compose.project=kanzlei-production
df -h /opt/kanzlei-erp
```

Inspect container logs without printing environment files or site configuration into
CI logs. Maintenance one-off containers are labeled `io.kanzlei.deployment=true`.
Timeout and signal handling terminates them before recovery; explicit resume/restore
also removes surviving labeled tasks under the server lock after a hard interruption.
If Docker is unavailable, resolve that first. Never run parallel manual Bench commands
while deployment or restore is active, and never delete the lock/pending marker simply
to bypass recovery checks.

### Resume the same migration

After diagnosing the failure, use the **exact** release, image, commit and tag from
`pending.json`. This uses the existing pre-update snapshot instead of backing up a
partially migrated database:

```bash
python3 /opt/kanzlei-erp/releases/RELEASE_DIR/deploy/manage.py \
  --root /opt/kanzlei-erp deploy \
  --release /opt/kanzlei-erp/releases/RELEASE_DIR \
  --image ghcr.io/nsivtsev/kanzlei-erp@sha256:DIGEST \
  --revision FULL_COMMIT_SHA --tag v1.0.1 --resume
```

For an interrupted first installation there is no prior snapshot; resume retries
site/app initialization without dropping the site. A marker reporting unsafe Docker
cleanup requires operator diagnosis and explicit restore where a complete backup
exists; it cannot be treated as a completed backup.

### Restore a selected snapshot

Restoring discards database and file changes since the chosen snapshot, including
files created after it. Ensure everyone is informed and the snapshot is the intended
recovery point. External effects such as already sent emails are not reversible by
a site backup. Use a reviewed copy of the manager from the deployment release:

```bash
python3 /opt/kanzlei-erp/releases/RELEASE_DIR/deploy/manage.py \
  --root /opt/kanzlei-erp restore \
  --backup /opt/kanzlei-erp/backups/BACKUP_ID \
  --confirm-site erp.example.com
```

The command verifies checksums and site identity before changing services. It checks
that the saved project name, platform and database password match the current
installation. It pulls the previous digest, restores site configuration, database and
both file trees, flushes the dedicated site's Redis caches/queues to discard jobs tied
to the abandoned database, migrates with the old image, and runs health checks.
Review and requeue necessary business work afterward. A failed restore keeps its
recovery marker and maintenance state; rerun the explicit restore after diagnosis.

Do not use `docker compose down -v`, reinstall the site, regenerate encryption keys,
or prune Docker volumes as a recovery shortcut. Switching an image tag alone is not
a database rollback. Keep the old GHCR digests available for every retained snapshot.
