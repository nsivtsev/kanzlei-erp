# AP-10 — сквозная приёмка и подготовка пилота MVP

> Реализовывать через `superpowers:executing-plans`: отрицательный тест → реализация → профильная проверка. Коммит — только по отдельному поручению.

## 1. Цель, основание и два результата

**Цель:** подготовить воспроизводимую сквозную приёмку и оценку качества, затем отдельно измерить Mistral и пригодность процесса для пилота.

**Архитектура:** существующие сервисы AP-03…AP-09 выполняют обработку; отдельные инструменты собирают наблюдения и считают метрики по независимой смысловой разметке. Fake проверяет процесс и контракты. Качество реального провайдера измеряется только по его фактическим результатам.

**Стек:** текущие Python/Frappe/ERPNext, MariaDB, Redis/RQ, jsonschema и инструментальное окружение AP-01. Новые production-зависимости, DocTypes, Custom Fields, HTTP endpoints и экран мониторинга не требуются.

**Основа:** `feature/ai-posteingang@d79ba0a`; AP-01…AP-09 завершены, рабочее дерево проверено чистым при составлении плана.

Пользователь согласовал два отдельных результата:

| Результат | Что означает завершение |
|---|---|
| **AP-10A — автономная готовность** | Расширенный синтетический набор, проверенные инструменты оценки, сквозной fake flow, эксплуатационная инструкция и честный отчёт о выполненных/невыполненных пунктах |
| **AP-10B — live-оценка и допуск пилота** | Измерение выбранного Mistral, проверка порогов и времени сотрудников, документированное решение о допуске |

AP-10A выполняется без ключа. AP-10B пока **NOT RUN**, весь AP-10 не объявляется завершённым. Даже успешный live smoke одного PDF не заменяет оценку holdout и замер времени.

Реальные документы не нужны для синтетической live-оценки. Их использование требует отдельного разрешённого контура и отдельного поручения. Основной сайт, deployment/PR, AP-11/12 и полный локальный CI image build не входят в работу.

### Разметка и freeze

- Сначала вручную зафиксировать смысловые actions/deadlines/recipients/candidates в annotations, затем отдельные fake extraction/review. Принятое/отклонённое человеком действие не определяет существование обязанности в документе.

- Дать каждому спорному соответствию статус `pending/adjudicated`, проверяющего и причину. Не имитировать двух независимых проверяющих двумя запусками одного агента. Неразрешённая разметка блокирует live quality verdict, но не разработку инструмента.
- Добавить отдельный профиль `ap10-v1`: ровно 42/12/30, минимальные знаменатели, покрытие тегов, исходный baseline и история рассмотрения holdout.
- Базовый validator уже допускает 12 development, >=4 holdout и 16…50 писем. Сохранить эту совместимость; добавить `--pilot-profile ap10-v1` для строгой проверки расширения. Обновить тест, который сейчас жёстко ожидает 16/12/4.
- Сохранить manifest/schema/catalog/gold hashes и prompt/code commit до первого измерения модели. Исправление gold даёт новую dataset version и новый отчёт.
- Прежние 4 holdout уже использовались в contract/fake-проверках. Честно показать это в отчёте; отдельно вывести результаты 26 новых кейсов. Не заявлять, что весь набор был технически скрыт. После настройки по live holdout последующий прогон не считается новой независимой оценкой без нового набора.
- Новые PDF с видимой synthetic-маркировкой отрендерить Poppler и визуально проверить, включая приложения/сканы. Старые 16 повторно визуально не проверять при неизменных bytes.

**RED→GREEN:** перепутанный split семьи, изменённый исходный PDF, недостающий gold, дубли ID, недостаточные 15 deadlines и пропущенный класс → ожидаемый отказ → валидный расширенный набор проходит.

## 4. Контракты оценки и сбор наблюдений

### Разделить входы

Оценщик принимает manifest, observations, judgments и, при наличии, timings/billing. У всех строгие JSON-схемы: версии, запрет неизвестных полей, реальные даты, безопасный parser, локальные refs, пути внутри разрешённого каталога.

`observations` содержит run ID оценки, case ID, PDF hash, provider/model/prompt/schema/code/configuration версии, фактические OCR/extraction или безопасную ошибку, кандидатов до ручного выбора, время этапов и provenance runtime Run. Для экспортированных синтетических данных допускается содержимое OCR/extraction; оно хранится отдельным артефактом, не в технических логах.

`judgments` содержит:

- one-to-one связи `gold_action_id → proposed_action_index`, оценку смысла и основание;
- факт соответствия срока, даты и привязанного действия;
- связи существенных gold facts с extraction JSON pointers/evidence;
- проверяющего, время и результат разбора спорных соответствий;
- привязку к hash конкретных observations и версии gold.

Индексы предложений относятся к конкретному неизменному результату модели, а не к Action UUID сотрудника. Повтор gold/proposal ID, неизвестный case, оценка от другой версии результата или неразобранное соответствие отвергаются. Несопоставленные gold — FN, предложения — FP. Совпадение заголовков не заменяет смысловую проверку; LLM-as-judge не добавлять.

### Сборщик Bench

1. Требовать явный site и подтверждённый локальный признак одноразового acceptance-сайта. Отказывать для основного сайта, произвольного пользовательского manifest и несинтетического набора. Не полагаться только на суффикс hostname.
2. Setup создаёт отдельный synthetic namespace и журнал собственных записей. Он не переиспользует реальные Customer и не меняет назначения ролей существующих сотрудников.
3. Передавать в provider только принятый PDF, реальный OCR и сведения о получении. Gold/catalog/reviews/expected Tasks не попадают в provider request. Catalog используется сервером для matching, как в AP-06.
4. Создавать Letter и Run через штатные сервисы. Для оценки сохранять результат анализа и matching до apply/ручных правок/подтверждения. Автоматически подтверждать письма при quality collection нельзя.
5. По существующему подходу jobs concurrency использовать отдельную именованную RQ-очередь и одноразовый worker без scheduler. Перенаправление dispatcher допустимо только в test harness; production workflow/lease/after-commit остаются штатными. Не останавливать общие workers и не очищать общий Redis.
6. Resume collection сверяет fingerprint конфигурации и run IDs; завершённые наблюдения не обрабатываются повторно. Failed/unknown-outcome не исчезает из отчёта. Новый платный запуск после неизвестного исхода требует явного действия, не скрытого retry скрипта.
7. Fake используется только для contract/process отчёта. `provider=fake` запрещено выдавать как успешную Mistral quality gate, даже при идеальных числах.
8. Live требует `--provider mistral --allow-external`, действующих Settings, разрешённой конфигурации и явного лимита запросов/документов. Ключ только через Password Settings; не CLI, файл отчёта или git. Нет fallback моделей и скрытых повторов.

В текущем AP-04 `AnalysisResult` не содержит usage/стоимость, а `attempt_count` AP-05 не равен числу HTTP-вызовов. Не выводить расходы из этих полей. В версии AP-10 импортировать фактический billing/usage export отдельным источником с периодом/валютой/основанием распределения. При его отсутствии стоимость `null / NOT MEASURED`; расчётная оценка подписывается отдельно, не как фактический счёт. Не расширять production-adapter телеметрией без конкретной необходимости и отдельного теста на отсутствие секретов.

**RED→GREEN:** fake как live, чужой hash, несинтетический источник, path traversal, повтор collection, утечка key/gold в запрос, неизвестный HTTP-исход → безопасный отказ/явный незавершённый результат.

## 5. Метрики и итоговый verdict

Все пороги AP-01 сохраняются. Для каждого: numerator, denominator, точное правило включения, case IDs ошибок и `PASS/FAIL/NOT MEASURED`. Округлённый процент не используется для допуска. Нулевой/недостаточный знаменатель не считается PASS.

| Метрика | Правило и порог |
|---|---|
| Action recall | Смыслово найденные gold actions / все gold actions holdout, **>=95%** |
| Action precision | Корректные самостоятельные предложения / все предложения, **>=90%**; дубли — FP |
| Recall действий с явным сроком | Найденные gold actions с explicit deadline / все такие gold actions, **100%** |
| Явные даты | Верная дата правильного действия / все gold actions с explicit deadline, **100%**; пропуск тоже ошибка |
| Relative dates | Самовольно вычисленных дат **0**; отклонённый валидатором raw ответ не скрывает попытку нарушения |
| Top-1 Customer | Верный первый кандидат в однозначных доступных случаях, **>=95%** |
| Top-3 Customer | Наличие допустимого gold Customer в первых трёх, **>=95%**; scope/исключения фиксируются заранее |
| Ambiguity / multiple addressees | Корректное обнаружение каждого соответствующего класса, **100%** |
| Проверенные цитаты | Точная страница и NFKC/whitespace совпадение с реальным OCR, **100%** |
| Evidence coverage | Существенные readable gold facts с подходящим verified evidence / все такие gold facts, **>=95%** |
| Активное время | Медиана отношений по заранее сопоставленным группам **<=0.70** ручного процесса |
| Утечки / автоподтверждения / дубли Tasks | **0** в выполненных acceptance-сценариях; это не статистическая гарантия отсутствия любых будущих ошибок |

Даты и evidence считаются по смысловому соответствию фактов, не по любому встреченному числу/цитате. Подтверждение цитаты по OCR не доказывает правильность OCR относительно PDF; отдельно показывать ошибки распознавания/смысла. Coverage denominator не состоит только из полей, которые модель решила вернуть.

Unreadable, schema failure, timeout и отсутствующий результат остаются в полноте действий и явных дат. Нельзя оценивать только успешные ответы. Дополнительно показывать coverage анализа, technical failure rate, долю manual fallback, правки по полям/действиям, лишние действия, полную задержку и стоимость письма/страницы.

Отчёт разделяет development, полный holdout и новые 26 holdout. Не объединять tuning и оценку в один процент. Неизвестный Customer и несколько адресатов имеют собственные ожидания, а не искусственно назначенный правильный Customer.

Проверить оценщик на небольшом независимом наборе ошибок: пропущенное действие, лишний дубль, переставленные даты двух действий, неверный Mandant, evidence с другой страницы, пустой OCR, неполный judgment, один из 30 результатов отсутствует. Значения numerator/denominator заранее выписаны вручную. Проверить точные границы 95/90/100% и 0.70.

CLI возвращает 0 для корректно построенного отчёта; режим `--require-gates` возвращает ненулевой код при FAIL или NOT MEASURED. Невалидный вход — отдельный код ошибки. Генерация отчёта сама по себе не означает допуск.

## 6. Сквозная автономная приёмка AP-10A

Не повторять все suites AP-01…09 без причины. Добавить компактный vertical suite и закрыть конкретные нерешённые риски:

1. Новый synthetic PDF → receive/replay/дубль → fake Run через настоящий RQ → apply → Mandant → явная review → confirm → ровно один набор Task/ToDo → календарная внутренняя дата → внешний срок/source → Customer Dokumente.
2. Manual при отключённом external provider: нет Run; unknown received date не заполняется; явное no-actions или пропуски планирования корректно подтверждаются человеком.
3. Потеря HTTP-ответа **после commit**, но до получения клиентом: transport harness отбрасывает ответ receive/confirm; тот же ключ восстанавливает историческую квитанцию без второй Task. Не имитировать это выбрасыванием исключения до commit. Для selection/correction переиспользовать существующее service/controller покрытие, расширить только при найденном пробеле.
4. Отключение обработки/отзыв прав между OCR и extraction: второй внешний запрос не происходит, Run остановлен. Re-enable не возобновляет его автоматически.
5. Redis dispatch failure и потерянная доставка: durable Run восстанавливается. Падение только собственного worker после OCR: checkpoint сохранён, неизвестный исход не вызывает автозапрос, явный повтор переиспользует OCR.
6. Correction с Completed старой Task: отдельный File, карантин, historical disposition, подтверждение замены другим разрешённым оператором; старый исполнитель не читает исходник.

Повторять действующие AP-05 concurrency-тесты целиком не требуется, если общий код не меняется; новый vertical тест должен использовать их подход независимого процесса для реального worker. Результаты AP-09 по responsive/темам и двум вкладкам остаются доказательствами при неизменном UI.

Браузер: один DE vertical fake flow через Page до Task/source/Dokumente; короткий RU manual flow для инструкции. Физический мобильный и повторный набор всех viewport не обязательны без изменений layout/локализации. Если обнаружена UI-ошибка — отдельный RED→GREEN и затронутый браузерный сценарий.

## 7. Эксплуатация и AP-10B

### Инструкция

В `docs/posteingang.md` описать:

- назначение Operator: обработка очереди; для одного Steuerberater роль явно назначается ему. System Manager — настройки/исправления. Customer/Task права всё равно обязательны;
- включение функции, fake/manual/mistral, конкретные модели, лимиты, выключенный автозапуск; старые письма сами не запускаются;
- ввод/ротацию секрета через Settings и epoch: старые Runs останавливаются, требуется явный новый запуск; сохранение настроек не обращается к Mistral;
- как различать Received/Queued/Processing/Error/Needs Clarification и безопасные коды; проверка worker/recovery/scheduler tick, next attempt и unknown-outcome;
- ежедневный ответственный и заместитель/эскалация. При одном сотруднике ответственный может быть один, но это не заменяет независимую проверку разметки/замера;
- ручную обработку, no-actions, отсутствие планирования, исправление ошибочного Customer, запрет перепривязки старых Tasks;
- мониторинг через существующую очередь/статусы, без помещения PDF/OCR/причин/секретов в технические логи;
- хранение оригинала/OCR/Run/Event/истории и evaluation artifacts: сроки утверждает владелец до реальных данных; автоматической очистки immutable audit пока нет. Не обещать неподдерживаемую функцию удаления;
- AP-04 не создаёт Mistral uploads, публичные URL или временные PDF: удаление удалённых uploads здесь `NOT APPLICABLE`, а не фиктивный cleanup job;
- условия реального контура, ответственных, контакты при ошибке, порядок остановки и восстановления. Не объявлять договорный/организационный допуск результатом unit-тестов.

### Порядок live-пилота — пока NOT RUN

1. Владелец предоставляет разрешённую конфигурацию и лимит внешних расходов; ключ вводится безопасно, не в чат/git/CLI. Перед запуском проверить актуальную официальную документацию моделей/endpoints и зафиксировать фактические имена. Не подменять их плавающими latest.
2. Зафиксировать gold, code/prompt/models/limits и dataset hashes. Сначала один development PDF smoke; затем development tuning при необходимости и новый freeze до holdout.
3. Обработать 30 holdout ровно выбранной конфигурацией; все ошибки сохраняются в оценке. Разметить смысловые соответствия и разобрать спорные случаи до verdict. Не выбирать лучший из нескольких прогонов задним числом.
4. Замерить ручной и AI-assisted процесс по заранее распределённым сопоставимым группам: минимум два участника, каждый в обоих режимах на разных письмах; одному участнику не давать одно письмо в двух режимах. Активное и полное время учитывать отдельно.
5. Если есть только один сотрудник, разрешён описательный usability-замер; метрика AP-01 об ускорении остаётся NOT MEASURED, порог не снижается. Независимого проверяющего/второго участника можно привлечь отдельно на синтетические данные.
6. Импортировать фактические расходы/usage либо явно оставить NOT MEASURED. Зафиксировать число запросов/повторов, если доступно, отдельно от attempt_count.
7. Принять решение: `GO_SYNTHETIC_PILOT`, `NO_GO` или `INCOMPLETE`. Любой FAIL/обязательный NOT MEASURED не даёт GO. Допуск реальных документов — отдельное решение владельца, не автоматический результат отчёта.
