# BL-042–043 — план защиты файлов и realtime Drive

> Реализовывать последовательно с использованием `superpowers:executing-plans`,
> `superpowers:test-driven-development` и `superpowers:verification-before-completion`.

**Цель:** исключить доступ к байтам Mandant через подставную запись File и передачу сведений о его файлах сотрудникам без актуального доступа.

**Архитектура:** общая серверная проверка соответствия File физическому объекту, вызываемая до сохранения и до доступа к хранилищу. Изменения списка передаются после commit адресным сигналом; клиент перечитывает данные через существующий API с проверкой прав.

**Стек:** Frappe 16, ERPNext 16, закреплённая версия Suite, Python, Vue, Socket.IO, локальное/S3-хранилище.

**Статус:** BL-042 и BL-043 реализованы и проверены 13 октября 2026. Полный CI образа прошёл; фактические результаты и ограничения: [отчёт приёмки](../reviews/2026-10-13-drive-security-verification.md). BL-044–049 и полная BL-050 остаются открытыми; production-деплой не выполнялся.

## 1. Объём и принятые решения

- Включены BL-042 и BL-043; из BL-050 — только необходимые для них регрессионные HTTP- и браузерные сценарии. BL-044–049 и полную BL-050 этим этапом не закрывать.
- Пользователь выбрал запрет второй записи File, ссылающейся на байты управляемого файла Mandant. Запрет действует даже для сотрудника с доступом к оригиналу: независимая запись не должна сохранять доступ после отзыва прав.
- Сохранить штатное разрешённое копирование обычных ERP-вложений. Проверять исходный документ и назначение; не вводить глобальную уникальность `file_url`, поскольку Frappe законно использует общий URL для копий вложений.
- Пользователь выбрал адресный сигнал обновления с последующим перечитыванием списка. В сигнале нет имени файла, пути, URL, Customer или сериализованной записи File.
- Существующие подозрительные ссылки блокировать при использовании и показывать в административном отчёте. Не удалять записи, не переносить байты и не исправлять связи автоматически.
- Работа локальная, на искусственных данных. Production-деплой — отдельный выпуск через существующий процесс.

Выбран вариант с двумя уровнями защиты. Только валидация сохранения оставила бы доступ через ранее созданные ссылки и операции, обращающиеся к диску до `save()`. Отдельный реестр зависимых ссылок потребовал бы новой модели прав и противоречил выбранному запрету таких ссылок.

## 2. Что подтверждено в текущем коде

- `kanzlei_erp/mandant_drive.py`: `prepare_file()` защищает записи с `kanzlei_drive_customer`, но обычная запись без маркера остаётся вне проверки пути защищённого объекта.
- Suite `drive/overrides/file.py`: при изменении обычного File проверяется допустимость локального пути, а не принадлежность байтов этому File. Frappe при создании использует точное сравнение URL и допускает обход через владельца исходной записи.
- `File.before_insert()` Frappe может прочитать и сохранить содержимое раньше `before_validate`; одной поздней проверки в document hook недостаточно.
- Suite читает и меняет хранилище несколькими путями: FileManager, прямое скачивание, Range, ZIP, WebDAV и операции с папками. Некоторые изменения происходят до последующего сохранения File.
- Suite `drive/api/files.py` отправляет `list-add` всему сайту с результатом `prettify_file(drive_file.as_dict())` и без ожидания commit. `prettify_file()` не удаляет внутренние поля.
- `GenericPage.vue` вставляет полученную из события запись прямо в список. Найдены также обработчики `list-update`, `list-remove`, `client-rename`; серверных отправителей этих трёх событий в проверенном Drive-коде не найдено.
- `drive-download-status` адресован пользователю, но ошибки передаются как `str(e)`. Стандартные уведомления Frappe `doc_update` и `list_update` также требуют проверки: подписка на комнату документа сама по себе не подтверждает права после их отзыва.

## 3. BL-042: соответствие File хранимому объекту

### Шаг 1. Зафиксировать обход тестами

Расширить `kanzlei_erp/tests/test_mandant_drive.py` и добавить отдельный модуль `kanzlei_erp/tests/test_drive_storage_security.py` для матрицы путей и операций.

Создать Mandant, сотрудника с записью, сотрудника с чтением и постороннего. Загрузить XML/PDF с известными байтами; посторонний создаёт собственный обычный файл и пытается заменить его URL на URL защищённого. Повторить для нового File и для владельца оригинала после отзыва прав Customer. До исправления тесты должны воспроизвести чтение через подставную запись; destructive-сценарии выполнять только на отдельных тестовых файлах.

### Шаг 2. Общая проверка хранилища

Создать внутренний модуль `kanzlei_erp/drive_storage.py` со следующими контрактами, без whitelisted API:

- `validate_file_binding(doc, previous=None)` — проверка предлагаемой привязки до любых побочных действий жизненного цикла File.
- `require_storage_access(file, operation, user=None, target=None)` — проверка сохранённой записи, текущих прав, источника и назначения до чтения, копирования или изменения хранилища. Для отказа использовать `frappe.PermissionError` без раскрытия чужого пути/клиента.
- `audit_storage_aliases()` — административная проверка без записи: список конфликтующих File и категории нарушения; не возвращать её результаты обычному пользователю.

Общие правила реализации:

- Различать локальный путь и S3 object key. Локальные URL приводить к реальному пути внутри разрешённых каталогов сайта, включая `/files/` → `public/files/`; учитывать разрешение symlink. S3 URL декодировать по существующему формату Suite, сохраняя семантику object key: файловый `resolve()` к нему неприменим.
- Проверять фактическую интерпретацию URL всеми поддерживаемыми входами; обходы через начальный `/`, кодирование, `.`/`..`, URL текущего сайта и S3-wrapper должны давать одинаковое решение либо отклоняться до I/O. Внешние HTTP(S)-ссылки остаются ссылками и не становятся разрешением читать внутреннее хранилище.
- Источник истины — сохранённые File и Customer, а не переданный клиентом маркер, владелец или первая найденная запись с таким URL. Учитывать все записи, разрешающиеся в тот же объект; конфликт нельзя скрыть обычной записью, найденной первой.
- Защищать сами объекты, поддеревья управляемых папок, thumbnail и trash объектов Mandant. Для flat storage проверять идентичность ключей, для иерархического — также границы каталогов. Операция над родительским каталогом не должна затронуть защищённое поддерево через подставную папку.
- Если хранилище принадлежит управляемому File, другая запись не может использовать его ни для чтения, ни для изменения, ни для удаления. Для самого File сохраняются текущие права Customer; смена типа, приватности, папки, attachment/content-полей не снимает защиту.
- Обычным File запретить произвольную смену привязки к существующим чужим байтам. Разрешённые операции Suite и копирования ERP выполняют явную проверку источника и назначения. Не доверять переданным JSON-флагам `file_created`, `ignore_permissions` или `copy_from_existing_file`.
- Для легитимной установки/смены ключа использовать узкий серверный контекст с идентификатором File, операцией и разрешёнными исходным/целевым ключами. Простой глобальный флаг «разрешено менять storage» недостаточен. Проверять до действия и сбрасывать контекст в `finally`.
- В первой реализации не менять схему данных: строить соответствия по сохранённым File; переиспользовать их только внутри одной операции/запроса и инвалидировать после изменений. Перед записью перечитывать затронутые File под блокировкой; долгоживущий кэш прав не использовать.

### Шаг 3. Подключить проверки ко всем входам

Расширить `kanzlei_erp/suite_file.py`, hooks Kanzlei и воспроизводимые патчи `deploy/frappe-mandant-access.patch` / `deploy/suite-mandant-access.patch`.

- Проверка `before_insert` должна выполняться **до** вызова базового Frappe, способного прочитать файл. Проверки обновления, приватности и удаления — до вызова соответствующего базового метода и файловых операций.
- Покрыть REST File create/update/delete, `frappe.client`, Desk save, `upload_file` с URL/library reference, стандартные attachment-copy и методы File. Проверка не должна существовать только в override whitelisted-метода: внутренние вызовы также проходят общий guard.
- Подключить проверку перед выдачей байтов/редиректа: Drive download/preview/Range/thumbnail, Frappe private-file с `fid` и без него, File content, S3 fetch, сборка и получение ZIP, WebDAV GET/HEAD.
- Подключить проверку источника и назначения перед upload/overwrite, rename/move, trash/restore/delete, COPY и WebDAV PUT. Проверять также отложенную очистку и rollback: отклонённая подставная запись не должна удалить оригинал при уборке.
- Ранее сохранённую подставную запись исключать из доступа через Frappe/Suite permission overrides; независимо от этого блокировать её на границе хранилища. Не давать владельцу и Suite Admin обходить проверку.
- Разрешённое копирование обычного ERP-вложения сохраняет текущую модель общего URL и права исходного/целевого документов. Реальное копирование байтов через штатный Drive/WebDAV остаётся отдельной операцией с новым объектом; это не разрешает переиспользовать ключ оригинала.
- Существующие preview-token и готовый ZIP повторно проверяют права и корректность привязки при использовании. Новые проверки не заменяют уже реализованную проверку отзыва прав.

Политика уже выданных S3 presigned URL не расширяется этим этапом: они живут до истечения срока. BL-042 проверяет, что подставная запись не может получить такой URL. Немедленное аннулирование ранее законно выданной ссылки потребует отдельного изменения способа доставки S3.

### Шаг 4. Регрессии и аудит

Проверить обычные папки, загрузку через ERP и Drive, переименование, перемещение, восстановление, независимое копирование и ERP attachment-copy. Отклонённые операции должны сохранять SHA-256, наличие и расположение оригинала. В моках хранилища проверить отсутствие вызовов чтения/записи/удаления до отказа, включая rollback.

Административный аудит использует тот же resolver, охватывает active/trash и конфликтующие записи независимо от маркера. Добавить вызов в инструкцию выпуска; найденные конфликты требуют ручного разбора без автоматического исправления.

## 4. BL-043: адресные уведомления после commit

### Шаг 5. Серверный контракт и доставка

Создать `kanzlei_erp/drive_realtime.py`. Через точку расширения в патче Suite заменить глобальный `list-add` для Kanzlei на событие **`drive-folder-changed`** с payload **`{ "folder": "<File ID>" }`**.

- Во время операции собирать только идентификаторы изменённых папок; объединять дубли в пределах транзакции. При rollback не отправлять ничего.
- После успешного commit заново получить сохранённое состояние и вычислить получателей. Не готовить список разрешённых пользователей до commit и не полагаться только на `publish_realtime(after_commit=True)` с заранее вычисленными адресатами.
- Получатели — включённые System User с текущим правом чтения папки и изменившегося объекта. Для Mandant применять Customer permissions, для обычной папки — существующие права Suite. Guest, Website User и отключённые пользователи сотруднический сигнал не получают.
- Отправлять явно в `user:<user>` через параметр `user`; не использовать общую комнату сайта, DocType или долгоживущую подписку как доказательство доступа.
- Для move/удаления сохранить до операции минимальный контекст исходной папки и Mandant. После commit проверять актуальные права на этот контекст; старая и новая папки обновляются независимо, без раскрытия перемещённого файла. Ошибка уведомления после commit логируется и не превращает успешно сохранённую загрузку в ошибку.
- Для первого этапа достаточно пакетно получить активных сотрудников и вычислить права штатным API с кешированием в рамках одной рассылки. Не создавать отдельный реестр подписчиков или прав; не считать число онлайн-сессий источником авторизации.

### Шаг 6. Закрыть другие события с теми же данными

Добавить в тесты перечень реальных отправителей событий Drive и стандартного жизненного цикла File.

- Загрузки, rename/move и trash/restore/delete используют новый путь уведомления; `list-add` с сериализованным File больше не отправляется. Другие приложения Suite не переводить на новый протокол.
- Для управляемого File исключить широкую рассылку стандартных `list_update` и отправку `doc_update` в комнаты, где мог остаться сотрудник после отзыва прав. Нужные стандартному Desk события направлять адресно после повторной проверки прав. Так же проверить delete/docinfo и File presence; события с идентификатором управляемого File не должны уходить ранее подписанному пользователю без актуального доступа.
- `drive-download-status` остаётся адресным, но перед каждым сообщением проверяет актуальный доступ к выбранным сущностям и членам архива. При отзыве прав допустим только общий отказ по принадлежащему пользователю токену, без сведений о файлах. Вместо `str(e)` передавать безопасный код/сообщение; подробности ошибки остаются в серверном журнале.
- Зафиксировать отсутствие серверных отправителей для устаревших `list-update`, `list-remove`, `client-rename`; убрать клиентское доверие их произвольным payload в изменяемом компоненте.

### Шаг 7. Клиент Suite

В `GenericPage.vue` подписаться на `drive-folder-changed` и перечитывать список существующим API. Для открытой папки реагировать на совпадающий ID; для активных агрегированных списков — обновлять текущую выборку, сохраняя фильтры и сортировку.

Сгруппировать частые сигналы задержкой 150 мс, с максимум одним запросом в полёте и одним отложенным обновлением. Перечитывать первую страницу, сбрасывать устаревший pagination cursor; сохранять выделение только для оставшихся строк. При смене маршрута игнорировать запоздавший ответ. При размонтировании снимать подписку и таймер. На 403 очищать список/выделение и показывать отказ, при сетевой ошибке — штатную ошибку и повтор; не выдавать ошибку за пустую папку.

Дополнить `GenericPage.test.ts` проверками сигнала, объединения событий, pagination, смены страницы, отказа и cleanup. Новые клиентские изменения и тесты должны входить в отслеживаемый патч Suite, а не оставаться только в локальном checkout зависимости.

## 5. Приёмка, последовательность и выпуск

### Матрица обязательных проверок

| Область | Сценарии и ожидаемый результат |
|---|---|
| Подмена File | Создание/изменение через HTTP и ORM, известный URL, собственная запись, унаследованные/подставленные flags: отказ до I/O |
| Старые ссылки | Искусственно сохранённый alias до исправления: чтение, изменение, удаление и обход через родительскую папку запрещены; аудит его находит |
| Права | Читатель, писатель, посторонний, бывший владелец, Suite Admin после отзыва: права Customer соблюдаются |
| Пути | Local flat/hierarchical, кодирование, symlink, S3-wrapper/object key, trash/thumbnail; внешняя HTTP(S)-ссылка остаётся работоспособной |
| Выдача | Download, preview-token, Range, private URL с/без fid, ZIP и WebDAV: alias не получает байты; законный доступ работает |
| Сохранность | Rename/move/overwrite/delete и rollback отклонённой операции не меняют оригинал; положительные сценарии обычных файлов и ERP-copy проходят |
| Realtime | Не менее четырёх сессий: писатель, читатель, посторонний, пользователь с отозванным доступом; обновления получают только текущие разрешённые сотрудники |
| Транзакции | До commit и после rollback сигналов нет; отзыв доступа между операцией и callback исключает получателя; повторные изменения дают один сигнал папки |
| Старые подписки | Открытая File/Drive-комната до отзыва не раскрывает последующие имена, ID файлов, пути или привязки через стандартные события |
| Клиент | Разрешённый сотрудник видит файл без ручной перезагрузки; сигнал не содержит записи; нет дублей, зависших подписок и применения ответа к другой папке |

Тесты реального HTTP/realtime вынести в отдельный сценарий `scripts/verify-drive-security.py` для одноразового CI-сайта. Использовать настоящие сессии и Socket.IO, не ограничиваться моками `publish_realtime`. Создание/очистка fixtures выполняются только на явно обозначенном тестовом сайте; пароли и cookie не писать в отчёт. Добавить сценарий в `scripts/ci-image.sh` после запуска backend/websocket. Существующий production smoke-check с Administrator не запускать для этих негативных сценариев.

### Порядок работы

1. Воспроизвести BL-042 красными тестами, внедрить storage guard и добиться зелёных проверок BL-042.
2. Воспроизвести BL-043 красными тестами, внедрить серверную доставку, затем клиентское перечитывание.
3. Выполнить HTTP/realtime-приёмку, регрессии Frappe/Suite и сборку обоих frontend bundles.
4. Проверить патчи на чистой закреплённой версии и повторном применении. Обновить обработку локального checkout со старой версией патча: переход должен быть явным, без сброса посторонних изменений и без частично применённого исправления.
5. Подготовить отчёт `docs/reviews/2026-10-13-drive-security-verification.md` с фактическими результатами, версиями, ограничениями и аудитом событий. Обновить README и соответствующие BL только после прохождения критериев; сохранить уже имеющиеся пользовательские изменения в этих файлах.

### Готовность

Оба пункта закрываются только после подтверждения: подставная запись не даёт чтения, изменения или удаления защищённых байтов; разрешённое ERP-копирование и обычный Drive работают; посторонние и лишившиеся доступа сотрудники не получают новые сведения через realtime; разрешённые сотрудники видят обновления после commit. В плане и отчёте отдельно указывать оставшиеся ограничения, включая срок жизни ранее выданных S3 URL. Схема данных и существующие документы не мигрируют; для выпуска нужны согласованное обновление backend и Suite assets, перезапуск сервисов и обычные backup/migrate/build/cache шаги процесса deployment.
