# AI Posteingang — поэтапный план имплементации

> **Для агента-планировщика:** взять один этап AP-XX, проверить зависимости и подготовить отдельный подробный implementation plan через `superpowers:writing-plans`. Для исполнения подготовленного плана использовать `superpowers:executing-plans`. Этот документ задаёт объём этапов; он не поручает реализовать все этапы за один запуск.

**Цель:** получить проверяемый процесс обработки бумажного письма от загрузки PDF до подтверждённых документов и задач манданта.

**Архитектура:** Incoming Letter хранит источник, попытки AI-анализа и решения сотрудника. Серверный адаптер Mistral и фоновые задания готовят предложения; подтверждение создаёт обычные ERPNext Tasks. Действующие Customer, File, хранилище и Dokumente переиспользуются с проверками доступа.

**Стек:** Frappe/ERPNext v16, Python по `pyproject.toml`, Frappe jobs, MariaDB, текущий File/S3 слой, Desk JS, Node tests и Bench tests. Suite Drive подключается отдельным расширением.

**Ветка:** `feature/ai-posteingang`; исходная точка `homepage@27016ce`. **Статус:** AP-01…AP-09 завершены. Серверная приёмка AP-02 — PASS; визуальная проверка DE/RU пропущена по явному решению владельца 19.10.2026. AP-05 серверные, конкурентные и клиентские проверки — PASS; ограничение RU browser upload записано в результатах этапа. Живой Mistral smoke — NOT RUN. AP-06: matching, явный выбор, DE/RU и профильная регрессия — PASS. AP-07: атомарное подтверждение, защищённые Tasks, исправления, DE/RU и расширенная регрессия — PASS (24.10.2026). AP-08: Dokumente, защищённый источник Task, disk/MemoryS3, DE/RU и профильная регрессия — PASS (25.10.2026). AP-09: единый экран, защищённые проекции, конфликты, исправления, DE/RU 1440/390 и профильная регрессия — PASS (25.10.2026). AP-10 не начат.

**Проектное решение:** [AI Posteingang](2026-10-18-ai-posteingang-design.md). Все договорённости и ограничения этого документа применяются к каждому этапу.

## Как агент берёт этап

1. Прочитать `AGENTS.md`, проектное решение, этот план и результаты зависимых этапов; проверить рабочую ветку и несвязанные изменения.
2. Выбрать ровно один AP-XX. Если зависимость не завершена, описать недостающий контракт; не притворяться, что предлагаемый модуль уже существует.
3. Сверить указанные точки интеграции с текущим кодом. Пути новых модулей ниже — предлагаемые, а не уже существующие; изменения имён согласовать через контракт этапа, не создавая дубли.
4. Сохранить подробный план в `docs/plans/YYYY-MM-DD-ai-posteingang-apXX-implementation.md`: точные файлы, API/поля/права, миграция при необходимости, небольшие шаги реализации, проверки и критерии завершения.
5. В начале плана обозначить решения, которые агент может принять самостоятельно, и внешние условия, без которых конкретный этап нельзя закончить. Не блокировать работу на fake provider из-за отсутствующего ключа или договора.

7. После реализации записать результат и фактически выполненные проверки в таблицу. Этап завершён только при выполнении критериев; невыполненная внешняя проверка отмечается явно.

Внутри детального плана использовать короткий цикл: тест существенного поведения → реализация → профильная проверка → проверка интеграции → фиксация результата. Кодовые заготовки и точные тест-кейсы относятся к детальному плану этапа; заранее писать реализацию всех этапов в этом roadmap не требуется.

## AP-01 — Контракты и эталонные сценарии

**Результат:** следующие агенты используют единые состояния, поля и критерии качества.

**Объём:**

- Уточнить допущение «одно письмо на PDF», роли обработки общего входа, дату получения и случаи нескольких Mandanten в письме. При отсутствии ответа сохранить обозначенные в проектном решении консервативные настройки.
- Зафиксировать схемы извлечения, действия и evidence: поля, enum, `null`, номера страниц, типы сроков, ограничения количества/длины. Определить стабильный action ID, ревизию результата и идентичность повторного запроса.
- Описать переходы состояний, ручной ввод, отклонение действий, отсутствие манданта/исполнителя/срока, отмену и контролируемое исправление уже подтверждённого результата без потери истории и переписывания выполненных задач.
- Определить типы идентификаторов Customer и источники их истины; не переносить автоматически все значения `tax_id` в Steuernummer.
- Подготовить синтетические PDF и ожидаемые результаты: простой запрос, несколько действий, без действий, неоднозначный/неизвестный Mandant, дата/относительный срок/отсутствие даты, плохой скан, много страниц, инструкции внутри документа. Определить формат расширения до 30–50 писем для пилота.
- Задать до измерений численные пороги качества пилота и способ сравнения времени с ручной обработкой. Нулевая терпимость к утечкам, автоматическому подтверждению и дублям Tasks при retry не заменяет метрик извлечения.

**Ориентиры:** текущие `docs/research/2026-10-03-ai-mandantendaten.md`, `kanzlei_erp/fixtures/custom_field.json`, `kanzlei_erp/tests/test_work_schedule.py`; новые `docs/plans/ai-posteingang/contracts.md`, `kanzlei_erp/tests/fixtures/posteingang/manifest.json` и синтетические PDF рядом. Папка contracts создаётся в этом этапе.

**Приёмка:** у каждого состояния есть разрешённые переходы; все классы срока и решений представлены примерами; явно разделены факты источника, предложения AI и подтверждение человека. Синтетические файлы не содержат реальных Mandantendaten. Итоговый контракт позволяет написать AP-02 и AP-04 без повторного продуктового проектирования.

**Проверки:** валидность JSON/дат/ссылок на страницы и визуальная проверка созданных PDF. Ещё не оценивать качество Mistral по fake-ответам.

**Результат 18.10.2026:** [контракт v1.0](ai-posteingang/contracts.md), шесть JSON Schema, таблица переходов, 16 синтетических PDF / 18 страниц (12 development, 4 holdout), независимая смысловая разметка и ожидаемые OCR/extraction/review результаты. Все 64 пары состояний и 11 сценариев повторов/ошибок описаны как спецификация. [План и передача AP-01](2026-10-18-ai-posteingang-ap01-implementation.md).

**Фактически выполнено:** автономный validator — PASS; 43 unittest — PASS, включая негативные кейсы, provenance кандидатов, quarantine-сценарий и воспроизводимость SHA-256 всех PDF; Ruff 0.14.0 по конфигурации проекта — PASS; все 18 страниц отрендерены Poppler и визуально проверены. Инструментальные зависимости изолированы от приложения. Runtime permissions/конкурентность/живой Mistral не проверялись и не выдаются за завершённые: это AP-02…AP-10. Пороговые значения пилота зафиксированы до измерений; пилот ещё не запускался.

## AP-02 — Модель письма и границы доступа

**Результат:** Incoming Letter можно создать вручную с приватным оригиналом и безопасно открыть уполномоченным сотрудником.

**Объём:**

- Добавить минимальные DocTypes Incoming Letter, Run, Action, Event и настройки согласно AP-01; оригинал и попытки защищены от обхода через обычный CRUD.
- Ввести управляемую роль оператора без автоматической раздачи всем сотрудникам; настройки доступны только администраторам. Схема подтверждения пока закрыта.
- До привязки использовать права общего входа; после привязки — также текущие права Customer. Списки, Link search, дочерние записи и File применяют ту же политику.
- Покрыть доступ к байтам, превью и альтернативным URL, владельца файла, DocShare и Guest/Website User. Существующие File hooks дополнять, не заменять.
- Миграция добавляет структуры без анализа и перепривязки старых документов. Функция и внешняя обработка выключены по умолчанию.

**Ориентиры:** новые `kanzlei_erp/kanzlei_erp/doctype/incoming_letter/`, `incoming_letter_run/`, `incoming_letter_action/`, `incoming_letter_event/`, `posteingang_settings/` в том же каталоге DocTypes, `kanzlei_erp/posteingang_permissions.py`, `kanzlei_erp/tests/test_posteingang_permissions.py`. Текущие `kanzlei_erp/hooks.py`, `kanzlei_erp/drive_storage.py`, `kanzlei_erp/object_storage.py`, `kanzlei_erp/fixtures/custom_field.json`. Не создавать отдельное хранилище файлов.

**Приёмка:** оператор видит общий вход, обычный сотрудник/портальный пользователь — нет; подтверждённое письмо недоступно после отзыва прав Customer, включая байты и OCR. Прямое изменение защищённых полей отвергается сервером. Повтор миграции безопасен, исторические записи не меняются.

Причина расширения — новый владелец приватного File и композиция глобальных hooks. Проверить установку/повтор миграции на локальном тестовом сайте, не запускать полный CI image build.

**Результат 19.10.2026:** пять DocTypes, управляемая роль, выключенные defaults, серверная сборка Letter/File/Event, неизменяемый оригинал и наследуемые права. Обязательные document/query guards закрывают DocShare fallback Frappe; File/Suite/S3 guards защищают альтернативные URL, preview, aliases, token/ZIP и presigned выдачу. Поля приватных receipts/snapshots и выбранного Customer закрыты в generic списках; типизированные представления добавят AP-06/07.

**Фактически выполнено:** 41 профильный runtime test — PASS с Suite; без Suite 34 PASS и 7 ожидаемых skip. Регрессии Drive security / Mandant Drive / Object Storage — 26 / 41 / 19 PASS. S3 проверен на MemoryS3; live provider и конкурентность подтверждения относятся к последующим этапам.

## AP-03 — Приём PDF и точные дубли

**Результат:** PDF попадает в надёжную очередь до любого обращения к AI.

**Объём:**

- Серверная загрузка и минимальное действие в форме Incoming Letter: проверка PDF по содержимому, ограничений размера/страниц, доступности и читаемости; шифрованный/повреждённый файл получает понятный результат.
- Сохранить оригинал, серверные дату/автора загрузки, отдельно известную дату получения, источник и hash содержимого. Не создавать публичные ссылки.
- Идемпотентный ключ загрузки и обнаружение одинаковых байтов, включая параллельные запросы. Проверка существования дубля не раскрывает чужое письмо или его имя.
- Загрузка нескольких файлов выдаёт результат по каждому. Перезапуск браузера не теряет уже принятые записи. Не оставлять доступные незакреплённые файлы при ошибке сохранения.

**Ориентиры:** новые `kanzlei_erp/posteingang.py`, `kanzlei_erp/tests/test_posteingang_intake.py`, форма `kanzlei_erp/kanzlei_erp/doctype/incoming_letter/incoming_letter.js`; существующие `kanzlei_erp/object_storage.py`, `kanzlei_erp/suite_file.py` и стандартные механизмы File.

**Приёмка:** повтор и одновременная отправка одного upload request дают одно письмо; тот же PDF обнаруживается как точный дубль в разрешённой области. Нечитаемый файл не считается успешно проанализированным. Оригинал после сохранения скачивается с тем же hash. Дата получения не подменена временем загрузки.

**Проверки:** `test_posteingang_intake`, права AP-02 и затронутые File/S3 случаи. Один короткий браузерный сценарий загрузки и повторной загрузки; DE/RU для новых локализованных сообщений. Новые зависимости парсинга PDF обосновать и проверить в используемой среде.

**Результат 20.10.2026:** [AP-03 завершён](2026-10-20-ai-posteingang-ap03-implementation.md). Добавлены multipart приём, изолированная проверка PDF, закрытые квитанции, replay/дубли под site-scoped locks и минимальный DE/RU диалог в списке/форме. Доступный дубль открывает существующее письмо без изменения даты; недоступный не раскрывается. Неизвестный исход commit не приводит к безусловному удалению оригинала.

**Фактически выполнено:** 20 intake + 5 concurrency/commit runtime tests — PASS; 4 PDF + 3 Node — PASS. Регрессии AP-02 — 41 PASS, Drive security/Mandant Drive/Object Storage — 26/41/19 PASS, patch installer — 21 PASS. Без Suite — 10 PASS/10 ожидаемых skip. Две повторные миграции сохранили контрольные данные, Settings и роли. Реальный HTTP, ровно 20 MiB и превышение, DE/RU смешанная пачка/дубль/восстановление, asset build, Ruff/JSON/CSV/diff — PASS. S3-логика проверена на MemoryS3; live S3 и Mistral не проверялись. AP-04, commit, PR и deployment автоматически не выполнялись.

## AP-04 — Настройки и адаптер Mistral

**Результат:** один документ превращается в проверенный структурированный результат через общий интерфейс fake/real provider.

**Объём:**

- Выбрать актуальные OCR и extraction endpoints/models, способ передачи приватного файла и закреплённую версию SDK либо существующий HTTP-клиент. В детальном плане привести официальные источники и дату проверки.
- Серверные настройки: выключатель внешнего анализа, провайдер, отдельные модели OCR/анализа, секрет, timeout и лимиты. Браузер и обычные ответы API секрет не получают.
- Реализовать fake provider для обычных тестов; реальный адаптер принимает только проверенный файл сервера, не произвольный URL из PDF/клиента.
- Проверять схему, номера страниц, формат дат и соответствие цитат OCR. Отсутствующую/противоречивую опору помечать, не придумывать. Разделить ошибку сервиса, распознавания, валидации и содержательную неопределённость.
- Зафиксировать жизненный цикл удалённых uploads, временных файлов и производных данных; очистка после успеха/ошибки, отсутствие содержимого и ключей в диагностике. Не переключаться на другого провайдера автоматически.
- Синтетический smoke-запрос выполнять только при доступной разрешённой конфигурации; реальные клиентские данные подключаются после отдельного решения по контуру обработки.

## Правила проверки каждого этапа

Действуют локальные инструкции `AGENTS.md`. Запускать тесты изменённых модулей и непосредственно затронутых зависимостей. Для UI — короткий end-to-end сценарий; добавлять языки и viewport при изменении локализации/адаптивности. Для прав, хранения, миграций, зависимостей и сборки указывать конкретный риск, объясняющий расширение проверок.

Типовой вызов существующего Bench-модуля из корня репозитория:

```sh
docker compose --env-file .env -f .devcontainer/docker-compose.yml exec -T frappe bash -lc 'cd /workspace/development/frappe-bench && bench --site development.localhost run-tests --module kanzlei_erp.tests.test_mandant_documents'
```

Для нового модуля заменить только имя тестового модуля на созданный в соответствующем этапе. Не запускать ещё не существующие tests и не предполагать, что контейнер/сайт уже поднят. Если нужны изменение схемы или assets, детальный план явно включает локальную миграцию/сборку до проверки UI.

Примеры точечных JS-проверок и проверки diff:

```sh
node --test tests/mandant-documents.test.cjs
git diff --check
```

Успешная проверка не повторяется без изменения кода или отдельного оставшегося риска. После исправления повторяются затронутые проверки. Проверка документации не выдаётся за тест реализованной функции. Live API не является обычным обязательным условием offline regression tests.
